### 合规说明

- 全库**没有**金额、小计、合计、库存数量列：行金额界面实时算；单据合计查询时 `SUM(...)`；库存走视图（第 6 章）。
- 全库**没有**年龄等可导出字段。
- 外键录入一律下拉选择，落实"外键完整性约束"。

## 4. 主键策略与业务编号规则

| 对象 | 规则 | 示例 |
|---|---|---|
| user_id | BIGINT 自增 | 1, 2, 3 |
| customer_id | 前缀 KH + 4 位顺序号 | KH0001、KH0002 |
| supplier_id | 前缀 GYS + 3 位顺序号 | GYS001 |
| product_id | 前缀 SP + 4 位顺序号 | SP0001 |
| po_no | 前缀 CG + 8 位日期 + 3 位当天流水 | CG20261007001（2026-10-07 第 1 张） |
| so_no | 前缀 XS + 8 位日期 + 3 位当天流水 | XS20261007001 |

生成方式：由后端 Service 在新增事务内查询当前最大编号后递增生成，编号在界面上只读展示。（课程项目为单用户/低并发场景，该方式足够；不另建序列表。）

**语义约定（重要）**：单号中的日期是**制单当日的服务器日期**，编号一经生成永久不变；`order_date` 是单据的**业务日期**（允许选择其他日期）。二者不要求一致，单号只是"按日编排的唯一流水标识"，不是从 order_date 导出的数据，因此不构成冗余。

## 5. 完整性约束设计

### 5.1 三类完整性

| 类别 | 落实 |
|---|---|
| 实体完整性 | 每张表有主键，主键非空、唯一；明细表联合 (单据号, 商品编号) |
| 参照完整性 | 6 个外键（见 5.2），InnoDB 强制校验 |
| 用户自定义完整性 | CHECK：性别 M/F；角色 1/0；状态取值；数量 > 0；单价 ≥ 0；折扣 0~1 |

### 5.2 外键清单

| 约束名 | 从表.列 | 主表.列 | 删除策略 | 说明 |
|---|---|---|---|---|
| fk_po_supplier | purchase_order.supplier_id | supplier.supplier_id | RESTRICT | 有单据的供应商不能删 |
| fk_po_user | purchase_order.operator_id | sys_user.user_id | RESTRICT | 有经办记录的用户不能删 |
| fk_pi_po | purchase_item.po_no | purchase_order.po_no | CASCADE | 删主单自动删明细 |
| fk_pi_product | purchase_item.product_id | product.product_id | RESTRICT | 被引用商品不能删 |
| fk_so_customer | sale_order.customer_id | customer.customer_id | RESTRICT | 有单据的客户不能删 |
| fk_so_user | sale_order.operator_id | sys_user.user_id | RESTRICT | — |
| fk_si_so | sale_item.so_no | sale_order.so_no | CASCADE | — |
| fk_si_product | sale_item.product_id | product.product_id | RESTRICT | — |

### 5.3 业务规则（应用层与数据库共同保证，答辩演示点）

1. 删除任何记录前前端**必须弹出确认框**，确认后才发请求。
2. **已审核单据（status='1'）禁止删除、禁止修改明细**——Service 层先校验状态，拒绝操作；这是除外键外的第二层"完整性约束"。
3. 只有**已审核**单据的数量才计入 v_stock 库存。
4. 保存单据时主表与明细在**一个数据库事务**内提交：明细为空或任一明细商品重复/数量非法时整单回滚。
5. 停用来往单位/商品（status=0）后，不能再被新单据选择，但不影响历史单据。

## 7. 视图设计（3 个视图）

### 7.1 v_purchase_full（采购单完整信息视图）

用途：落实课程"联系表——视图的完整查询"。将明细与主表、供应商、商品、经手人连接，一次查出单据上的全部可读信息，采购单列表/详情/打印均基于该视图。

```sql
CREATE OR REPLACE VIEW v_purchase_full AS
SELECT
       pi.po_no,
       po.order_date,
       po.delivery_place,
       po.status,
       s.supplier_id,
       s.supplier_name,
       pi.product_id,
       p.product_name,
       p.spec,
       p.unit,
       pi.quantity,
       pi.unit_price,
       pi.discount,
       ROUND(pi.quantity * pi.unit_price * pi.discount, 2) AS amount,
       u.user_id,
       u.real_name AS operator_name,
       po.remark
FROM purchase_item pi
JOIN purchase_order po ON pi.po_no = po.po_no
JOIN supplier       s  ON po.supplier_id = s.supplier_id
JOIN product        p  ON pi.product_id = p.product_id
JOIN sys_user       u  ON po.operator_id = u.user_id;
```

### 7.2 v_sale_full（销售单完整信息视图）

```sql
CREATE OR REPLACE VIEW v_sale_full AS
SELECT
       si.so_no,
       so.order_date,
       so.delivery_place,
       so.status,
       c.customer_id,
       c.customer_name,

```

### 7.3 v_stock（商品实时库存视图）

用途：库存 = 已审核采购入库 − 已审核销售出库，实时计算、绝不存储，是"导出项不入库 + 视图"两大要求的集中体现。从未发生业务的商品库存显示为 0。

```sql
CREATE OR REPLACE VIEW v_stock AS
SELECT
       p.product_id,
       p.product_name,
       p.spec,
       p.unit,
       p.unit_price,
       COALESCE(pur.qty, 0) AS purchase_qty,
       COALESCE(sal.qty, 0) AS sale_qty,
       COALESCE(pur.qty, 0) - COALESCE(sal.qty, 0) AS stock_qty
FROM product p
LEFT JOIN (
        SELECT pi.product_id, SUM(pi.quantity) AS qty
        FROM purchase_item pi
        JOIN purchase_order po ON pi.po_no = po.po_no
        WHERE po.status = '1'
        GROUP BY pi.product_id
) pur ON p.product_id = pur.product_id
LEFT JOIN (
        SELECT si.product_id, SUM(si.quantity) AS qty
        FROM sale_item si
        JOIN sale_order so ON si.so_no = so.so_no
        WHERE so.status = '1'
        GROUP BY si.product_id
) sal ON p.product_id = sal.product_id;
```

> MySQL 8 视图中允许 FROM 子查询与 COALESCE；视图本身不存数据，每次查询实时执行。

## 8. 范式审查（1NF / 2NF / 3NF）

> 本章为开发前的正式范式核查。审查方法：列出函数依赖（X→Y 表示 X 决定 Y），逐表核对。外键列带来的是**参照依赖**，不属于范式要消除的函数依赖。

### 8.1 函数依赖清单

| 表 | 函数依赖 |
|---|---|
| sys_user | user_id → (username, password, real_name, gender, role, status)；username ↔ user_id（username 为 UNIQUE 候选键） |
| customer | customer_id → (customer_name, contact_person, phone, address, status) |
| supplier | supplier_id → (supplier_name, contact_person, phone, address, status) |
| product | product_id → (product_name, category, spec, unit, unit_price, status) |
| purchase_order | po_no → (supplier_id, operator_id, order_date, delivery_place, status, remark) |
| purchase_item | (po_no, product_id) → (quantity, unit_price, discount) |
| sale_order | so_no → (customer_id, operator_id, order_date, delivery_place, status, remark) |
| sale_item | (so_no, product_id) → (quantity, unit_price, discount) |

### 8.2 第一范式（1NF）——属性原子性

所有列都是不可再分的原子值，表中不存在多值列或重复组：

- 没有"客户信息（名称+电话）"类混合列；contact_person、phone、address 各自独立成列。
- `address` 作为一个完整地址字符串存储：本系统没有按省/市/区分别查询或统计的需求，地址在业务上作为一个整体使用（YAGNI），属基本项而非组合项。
- product.`spec`（规格型号）沿用课程课件案例的口径（课件案例商品属性即为"规格型号"），作为一个描述性基本项。
- `category` 为单分类（非多值标签）。

**结论：满足 1NF。**

### 8.3 第二范式（2NF）——消除部分依赖

2NF 只对联合主键表有约束。6 张单主键表上，任何属性都只能依赖完整主键，自动满足 2NF。

两张明细表（purchase_item / sale_item）联合主键为 (单据号, 商品编号)，逐个非主属性核查：

- `quantity`：该商品在本单中的数量，必须同时知道"哪张单 + 哪种商品"才能确定 → 完全依赖。
- `unit_price`：**本次成交单价**，随单据和商品两者变化（同一商品在不同单据中成交价可能不同）→ 完全依赖。
- `discount`：本次成交折扣，同理 → 完全依赖。

不存在只凭 product_id 或只凭单据号就能确定上述属性的情况，因此无部分函数依赖。

**结论：满足 2NF。**

### 8.4 第三范式（3NF）——消除传递依赖

逐表检查"非主属性之间"是否存在函数依赖（即非主属性 A 决定非主属性 B）：

- sys_user：各属性互相独立；username 与 user_id 互相决定，但 username 是**候选键（主属性）**，传递依赖要求中间决定因素不能反过来决定主键（此处 username↔user_id），故不构成传递依赖。
- customer / supplier：联系人、电话、地址、状态均直接依赖本单位编号，彼此不存在依赖（电话、联系人都归属于该单位，不互相决定）。
- product：分类、规格、单位、单价、状态直接依赖商品编号；分类不决定单位或单价（同分类商品可有不同单位、价格）。
- purchase_order / sale_order：往来单位、经手人、日期、交货地点、状态、备注直接依赖单据号；交货地点不由供应商/客户决定（交货地点是我方仓库，按单指定）。
- 两张明细表：数量、单价、折扣互相独立。

所有非主属性都只直接依赖主键（或联合主键整体），无传递依赖。

**结论：满足 3NF。**

### 8.5 三个边界说明（经核查均非范式违反，答辩备查）

1. **明细表的 unit_price 与 product.unit_price 共存不是冗余。**
   两者语义不同：product.unit_price 是商品档案的**当前标准价**（可变）；明细表 unit_price 是**历史成交单价**（不可变）。标准价未来调整后，历史单据仍必须按下单当时的真实价格结算，这是时态数据的标准保存方式，且它正是明细表 2NF"完全依赖 (单据号, 商品编号)"的依据。

2. **product 的 category、unit 以字符串值在多行重复。**
   形式上它们直接依赖 product_id，无传递依赖，**满足 3NF**；但严格工程视角下，改名分类需更新多行，存在轻微更新异常隐患。本系统分类、单位均为固定枚举/下拉选项，由前端下拉约束输入一致性，课程规模下不单独建字典表（YAGNI）。如教师要求，可后续抽出 category_dict、unit_dict 字典表，不影响其他设计。

3. **单号（CG/XS+日期）中包含日期不是导出项冗余。**
   单号日期表示"制单日"（编号永久不可变），order_date 是可选择的"业务日期"，两者语义不同、允许不一致；约定见第 4 章。且 po_no 是主键，主键决定任何属性在范式上都合法。

### 8.6 审查总结

| 范式 | 结论 |
|---|---|
| 1NF 属性原子 | 满足 |
| 2NF 无部分依赖（明细表联合主键完全依赖） | 满足 |
| 3NF 无传递依赖 | 满足 |

另外，金额、合计、库存均为导出数据，按设计原则**故意不入库**（由视图/查询实时计算），不属于范式讨论范围。**数据库设计可进入开发阶段。**
